## 1. 战略转向：从 Web SaaS → iOS App 主战场

**时间**：2026-06-08
**触发**：小范围用户调研发现

### 真实用户画像

| 之前的假设 | 真实情况 |
|---|---|
| 主播用 OBS 在 PC 推流/录屏 | 主播用**手机**直播，**iOS 自带录屏** |
| 主播会主动打开电脑做复盘 | 主播**不会主动开电脑** |
| 复盘 = PC 大屏看报告 | 复盘 = 手机上刷报告 |
| Web 是主战场 | **iOS app 是主战场**，Web 降级为辅助 |

### 决策

1. ✅ iOS app 从「M3+ 可选」**升级为 M2 主战场**
2. ✅ Web 端继续维护但不再投资新功能（MCN 老板看团队数据的辅助场景）
3. ✅ PWA 路线作废（iOS Safari 限制：无后台上传、无相册深度集成、无 APNs、不能唤起抖音 OpenSDK）
4. ✅ Android 暂不做（验证 iOS 后再说）

### 已被推翻的旧假设

- ~~"做 Tauri 桌面 app 解决大文件上传"~~ → 用户根本不在 PC
- ~~"PWA 是最低成本的 app 化方案"~~ → 关键能力 iOS Safari 都不给
- ~~"OBS 横屏录屏是主流"~~ → 实际全是**抖音手机直播竖屏 9:16**

## 3. "上传即开工"核心交互（owner 2026-06-08 提出）

**决策**：用户在 app 上传视频后**无需等待**，立刻进入复盘工作台开始记笔记。

### 为什么这是对的判断

把"等待时间"变成"使用时间" — 是体感优化的天花板招式。
任何"加快服务端分析"的努力都不如"让用户上传后立刻能干活"。

### 实现路径

1. **本地立即可用的功能**（无需 server）：
   - 视频播放器（PHPicker 选完即播）
   - 时间轴拖拽
   - 笔记 + 时间锚（本地存 SwiftData，后台 sync）
   - 标记"高光时刻候选"（端侧粗识别 + 手动标记）

2. **渐进式出现的功能**（边跑边显示）：
   - **端侧 ASR**（Apple Speech Framework）：边识别边显示话术；标题"正在识别 30%..."
   - **端侧粗识别亮点**（音量峰值 + 帧差异）：30 秒内出"3 个可能亮点候选"

3. **服务端跑完后通知**：
   - AI 评分、Top3 改进点、洞察等 → 跑完发 APNs 推送
   - 用户点通知直达报告页

详细流程见 [02-ux-flow.md](02-ux-flow.md)。

### 推翻的旧设计

- ~~"上传完成后显示'分析中'阻塞页"~~ → 改为立刻进工作台
- ~~"AI 分析必须完整才能展示报告"~~ → 改为分阶段渐进式展示

## 4. 技术栈：Swift 原生（不用 React Native）

**时间**：2026-06-08
**决策人**：owner

### 选 Swift 原生的代价（owner 接受）
- 学习期 2-3 个月（Swift + SwiftUI + AVFoundation）
- React 业务代码 0 复用
- 永久放弃 Android（除非未来再花 6 个月学 Kotlin）

### 选 Swift 原生的收益
- AVFoundation 视频处理性能 = 苹果亲儿子（vs RN 桥接性能损失 30-50%）
- SwiftUI 60fps 丝滑无掉帧
- 系统集成深度：PhotoKit / ShareKit / BGTaskScheduler / Live Activity / 灵动岛全是原生 API
- 启动速度 / 包体积 / 调试工具 / 新 iOS API 跟进速度全部最优
- 苹果审核 4.2 风险归零

### 备选方案（已放弃）
- ❌ React Native（owner 决定要原生质感）
- ❌ Capacitor（套壳被苹果拒风险高）
- ❌ Flutter（Dart 学习成本 + 跟 React 知识 0 复用）

## 5. 边用边等的技术风险（待解决）

### 风险 1：端侧 ASR 准确率
- Apple Speech Framework 中文准确率：✅ 一般用语 90%+；⚠️ 美妆专业词 / 品牌名识别率不确定
- 后端 ASR（阿里云 / Whisper）准确率：~95%
- **缓解**：端侧出"快速版" + 后端出"精准版"，后端结果回来时**自动 diff + 替换**

### 风险 2：本地笔记 vs 服务端冲突
- 用户在 app 本地记笔记同时，server 也在生成"AI 建议笔记"
- **缓解**：用户笔记永远优先；AI 建议显示为独立的"AI 建议"区，不混入用户笔记

### 风险 3：离线场景
- 用户在没网时录完直播、想立刻看视频记笔记
- **缓解**：app 完全离线可用（视频本地、笔记 SwiftData 本地），有网时再同步上传

## 6. 端侧 ASR 分层（owner 2026-06-08 拍板）

**决策**：
- **MVP 用 Apple Speech Framework 做端侧快速占位**（中文够用、低功耗、官方稳定、免下载模型）
- **服务端阿里云 ASR 做精准覆盖**（已有 pipeline）
- **Whisper.cpp on-device 推迟到 M3 候选**（不进 MVP）

**为什么 Whisper.cpp 不进 MVP**：
- 跟服务端 ASR 角色重叠，做两遍精准识别
- 端侧性能现实：small 模型 470MB + iPhone 13 Pro 跑 30 分钟视频 8-12 分钟，**比上传到服务端跑还慢**
- 首次下载 470MB+ 用户流失
- 维护两套 ASR diff/合并逻辑

**触发条件做 Whisper.cpp**：用户反馈"端侧 Apple Speech 不准" + "服务端等待难忍" + 设备性能跟上（iPhone 15+ Neural Engine 更强）

## 7. 笔记富文本支持（owner 2026-06-08 拍板）

**决策**：
- M2 MVP **支持富文本**
- **存储用 Markdown 字符串**（可移植、可导出、跟 backend / web 端通用）
- **显示用 `AttributedString(markdown:)`**（iOS 15+ 原生 API，无第三方依赖）
- **编辑 UI 用极简工具栏版**（不做 WYSIWYG）

### 极简编辑器交互

笔记输入框底部固定 4 个按钮：
- [B 加粗] → 选中文本包 `**xxx**`
- [I 斜体] → 选中文本包 `*xxx*`
- [H 高亮] → 选中文本包 `==xxx==`（GFM 高亮）
- [@时间锚] → 自动插入当前播放时间戳 `[02:35]`

显示时全部 Markdown 渲染。

### 为什么不做 WYSIWYG
- iOS 没有现成的 SwiftUI 富文本编辑器组件
- 自己写 WYSIWYG 工作量大（光标定位、选区状态机、撤销栈）
- 第三方库（MarkdownUI / RichTextKit）增加 50KB+ 包体积 + 学习成本
- 极简版已经够主播写"02:35 这段逼单效果不错，下次可以学"这种笔记

### M3 候选
- 笔记 @ 引用 AI 洞察（"AI 说开场太短了，确实"自动链接）
- 笔记导出 PDF / 分享卡片

## 8. 高光切片端侧 + 服务端分层（owner 2026-06-08 拍板）

> ⚠️ **2026-06-10 已被 §10 大幅修正**：放弃"app 内剪辑 + 发抖音"，改为"高光定位器 + 导出给剪映"。
> 下面的"端侧/服务端识别分层"逻辑仍有用（识别高光），但"切片/合并/加入切片"这套**剪辑器交互作废**。

**决策**：
- **端侧轻量识别**（音量峰值 + 帧差异 + 端侧 ASR 情绪词检测）→ 3 个候选立即可见
- **服务端精准识别**（基于完整 OCR + 评分 v5 + insight engine）→ 5-7 个精准切片
- **合并策略：服务端为准 + 尊重用户已选**

### 合并策略详细
1. 端侧给 3 个候选 → 用户可立即预览、可点"加入切片"
2. 服务端结果回来后 →
   - 端侧候选 ∩ 服务端候选（时间重叠）：用服务端时间区间替换（更精准）
   - 端侧候选 - 服务端候选（端侧有服务端无）：
     - 如果用户已点过"加入切片" → 保留（尊重用户操作）
     - 如果用户没操作过 → 标灰 + 提示"AI 评估优先级较低"，用户可手动恢复
   - 服务端候选 - 端侧候选（服务端新增）：追加到列表
3. UI 上有"AI 推荐"标记区分服务端识别的优先项

### 为什么这么设计
- 避免"我刚选的候选怎么没了"焦虑
- 服务端结果是 ground truth，但用户的选择优先级更高
- 端侧候选是"快速预览"，服务端是"精准建议"

## 10. 切片功能重定义：不做剪辑器，做"高光定位器"（owner 2026-06-10 拍板）

**触发**：owner 质疑——"用户用剪映直接剪更方便，剪映功能还多得多，切片到底有没有优势？"

### 核心判断：做剪辑器没有优势，砍掉

- **剪映在"剪辑"上降维碾压**：字节亲儿子、免费、海量模板/字幕/音乐、主播早装早会、肌肉记忆。
  我们做一个简陋切片器去刚剪映 = 拿石头砸坦克。
- **"一键发抖音"也不是壁垒**：剪映剪完本来就能一键发抖音（同字节生态无缝）；
  我们绕"app 内剪 → 抖音 OpenSDK"体验还更差。

### 关键区分：切片有两个动作，价值完全不同

| 动作 | 谁强 | 做不做 |
|---|---|---|
| **找哪段值得切**（识别高光） | ✅ 我们的强项（OCR/弹幕/评分/AI） | **做** |
| **怎么剪**（剪辑/特效/字幕） | ❌ 剪映碾压 | **不做** |

**主播真正的痛点不是"没工具剪"，是"2 小时回放里哪 30 秒值得发"** —— 剪映不知道哪段是高光，我们知道。

### 正确形态：高光定位器 + 导出给剪映

```
我们的 app：AI 列出「这 5 个高光时刻，按转化/互动排序，附原因+评分」
           → 主播点「导出这段」→ 存相册 / 系统分享 sheet
           → 主播在剪映精修 → 发抖音
```

我们负责"切哪里"（AI 强项），剪映负责"切得好看"（剪映强项），各打各的强项，不硬刚。

### 决策

1. **"切片" tab 改名为"高光时刻"**：列 AI 识别的高光候选（时间段 + 为什么 + 评分），点击跳转预览。
2. **导出 = 系统分享 sheet / 存相册**，**不做 app 内剪辑器**。
3. **放弃"一键发抖音"执念**：不是护城河，剪映替我们做了。
4. **不接抖音 OpenSDK**（系统分享就能转剪映/相册）—— 顺带解锁了之前卡住的 OpenSDK 依赖，Sprint 6 不再被它阻塞。

### 影响

- §8 的"剪辑器交互 / 切片合并"作废；"端侧+服务端识别高光"逻辑保留（用于定位）。
- `03-roadmap.md` Sprint 6 重定义：从"切片+抖音发布"→"高光定位器（导出给剪映）"，去掉 OpenSDK 阻塞。
- 产品聚焦更清晰：**我们是"教练 + 高光定位"，不是"又一个剪辑工具"**。

### 待验证 🔍

- 客户端切片导出原始片段（AVMutableComposition 切 + 存相册/分享）可行性 —— 但视频在后端 MinIO 流式播，
  本地无原文件，导出需先下载该时间段或后端切。**M2 真做时再定**：后端切一小段 mp4 返回 URL 可能比客户端简单。
